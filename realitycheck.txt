3. Caddy Proxy Reality
==================================================

3.1 The draft Caddy block is not correct as written
- The proposed rule was:

  posterpro.sparkleserver.site {
    reverse_proxy /api/* localhost:8010
    reverse_proxy /* localhost:3010
  }

- That assumes the FastAPI app is mounted under `/api`.
- It is not.

3.2 What the backend actually exposes
- The FastAPI app includes routes like:
  - `/health`
  - `/listings`
  - `/ebay/auth/url`
  - `/sales/dashboard`
  - `/inventory`
- These are mounted directly at root in the backend app.
- Source:
  - `/opt/apps/posterpro/repo/backend/app/main.py`

3.3 Why this matters
- If Caddy proxies `/api/*` directly to the backend without stripping `/api`,
  then requests like:
  - `https://posterpro.sparkleserver.site/api/listings`
  will arrive upstream as:
  - `/api/listings`
- The backend expects:
  - `/listings`
- So those requests would fail unless `/api` is stripped first.

3.4 Media routing is also required
- PosterPro mounts `/media` from its storage directory.
- If uploaded images are meant to render on the live site, `/media/*` must also be proxied.

3.5 Correct Caddy pattern
- Use `handle /api/*` and strip the prefix.
- Proxy `/media/*` to the backend.
- Proxy the frontend separately.

Example pattern:

posterpro.sparkleserver.site {
    encode zstd gzip

    handle /api/* {
        uri strip_prefix /api
        reverse_proxy 127.0.0.1:<BACKEND_PORT>
    }

    handle /media/* {
        reverse_proxy 127.0.0.1:<BACKEND_PORT>
    }

    handle {
        reverse_proxy 127.0.0.1:<FRONTEND_PORT>
    }
}

3.6 Safer reload procedure
- Do not immediately reload after editing.
- First validate:
  - `caddy validate --config /etc/caddy/Caddyfile`
- Then reload:
  - `systemctl reload caddy`

4. Frontend Production Reality
==================================================

4.1 The frontend is a Next.js app
- The repo frontend is standard Next.js.
- It is not currently configured as a static-export-only site.
- Source:
  - `/opt/apps/posterpro/repo/frontend/package.json`
  - `/opt/apps/posterpro/repo/frontend/next.config.js`

4.2 The original directive about static serving is too optimistic
- The deployment note said to:
  - run `npm run build`
  - serve `out/` or `.next/` statically through Caddy
  - avoid a Node process in production

- That is not currently supported by the repo as-is.
- `next build` creates a production build, but not a static-export site by default.
- There is no export config in `next.config.js`.
- There is no evidence that `out/` will exist.

4.3 Practical deployment reality
- Until the frontend is explicitly adapted for static export, production should use:
  - `npm run build`
  - `next start` on a dedicated localhost port
  - Caddy reverse proxy to that Next server

4.4 Frontend API base must be configured
- The frontend uses:
  - `NEXT_PUBLIC_API_BASE`
- Default fallback is:
  - `http://localhost:8000`
- That is wrong for production if the public site is behind Caddy.
- Production should set:
  - `NEXT_PUBLIC_API_BASE=https://posterpro.sparkleserver.site/api`

Source:
- `/opt/apps/posterpro/repo/frontend/lib/api.js`

6. User Model / Bootstrap Reality
==================================================

6.1 The app currently assumes `user_id=1` in many places
- The frontend and backend repeatedly default to user 1.
- This is visible in:
  - analytics endpoints
  - sales endpoints
  - marketplace connection endpoints
  - frontend dashboard hooks and API helpers

6.2 Why this matters
- A clean production database may not have any user row at all.
- If no user exists with `id=1`, parts of the app may fail or return empty results.

6.3 Required deployment/bootstrap step
- Create a seed/bootstrap user before declaring the app functional.
- If admin auth is added, that bootstrap path should also define the first admin account.

8. Automation Safety Reality
==================================================

8.1 Autonomous mode exists
- PosterPro does contain autonomous-mode logic.
- It also includes Celery worker tasks and Celery Beat schedules for recurring operations.

8.2 Live-first risk
- Turning everything fully live immediately can trigger real automation behavior before the stack is verified.
- That is risky for a first production boot.

8.3 Safer first deployment posture
- First boot should use:
  - `AUTONOMOUS_DRY_RUN=true`
  - `SALE_DETECTION_DRY_RUN=true`
- After smoke testing and verification, those can be changed if desired.

12. Bottom Line
==================================================

The deployment goal is still achievable, but the original brief contains a few assumptions that are not true in the current repo/server state:

- backend port `8010` is already taken
- the backend is not mounted under `/api`
- the frontend is not yet set up as a static-only production export
- the homepage is currently the internal dashboard, not a marketing lander
- login/auth is not implemented yet
- admin backend is not implemented yet
- the app assumes `user_id=1`, so bootstrap data is needed

So the correct framing is:

Phase 1:
- deploy the existing repo safely on non-conflicting ports
- wire Caddy correctly
- configure secrets
- migrate DB
- start API, worker, beat, and frontend
- confirm health and smoke-test core functionality

Phase 2:
- build the public lander
- add login/auth
- add admin backend
- add the SparkleServer project card
- polish production UX

That is the actual reality as of this inspection.
